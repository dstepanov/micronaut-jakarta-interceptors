There is no Technology Compatibility Kit for Jakarta Interceptors. The specification page publishes none, and
interceptors are instead covered by the Technology Compatibility Kit of Jakarta Contexts and Dependency Injection,
in two forms:

* `jakarta.tck:cdi-tck-ee-impl`, which is deployed to a Jakarta EE runtime through Arquillian;
* `jakarta.tck.coreprofile:cdi-lite-tck-suite`, the CDI Lite suite of the Jakarta EE Core Profile, which needs no
application server and runs standalone.

Neither can be run against this module, and the reason is not the runtime they need: both are suites for the
*Contexts and Dependency Injection* specification, and their test classes drive an implementation through
`jakarta.enterprise.inject.spi.BeanContainer`, Arquillian deployments and the CDI rules of type discovery.
Micronaut has a dependency injection container of its own and implements none of that.

What can be run are the interceptor tests with their container access adapted. The
`org.jboss.cdi.tck.interceptors.tests` package of `jakarta.enterprise:cdi-tck-core-impl` carries the scenarios of the
Interceptors specification - the beans, the interceptor classes and the binding annotations its own authors wrote -
and they are ordinary Jakarta Interceptors code. The `cdi-tck-interceptors` module fetches those sources from Maven
Central at build time and compiles them with this module's annotation processor. It then runs the kit's own compiled
TestNG test classes unchanged, with a small `AbstractTest` bridge translating the Arquillian and CDI bean operations
they use into Micronaut operations. Nothing is vendored; the sources are Apache 2.0 licensed, as this project is.

The harness marks the kit's test methods it cannot run, each with its reason, so that what is not covered is as
visible in a test report as what is. What it cannot run expects eager interceptor creation. For tests that expect
an Arquillian deployment to fail, the bridge reads the original deployment archive, compiles its classes with
Micronaut's annotation processor and requires that compilation to fail. The scopes and producer methods of Jakarta
Contexts and Dependency Injection are read as their Micronaut equivalents, so that the scenarios themselves can be
created.

Where the kit asks a bean manager how many interceptors a set of bindings resolves to, the count is asserted of the
interception instead. Each of those binding sets is the binding set of an element of the deployment it is taken
over, so a count of one is that the one interceptor interposed on that element and that no other did; see
`BindingResolutionTckTest`.

The kit also describes two deployments a container is required to reject rather than run. Nothing is deployed here,
so each is handed to the compiler instead, with this module's annotation processor on it, and the compilation is
required to fail: what a container reports as it starts, this module reports as it builds.

Running them found four defects that the tests of this repository had missed, each now covered by a test here as
well: `proceed()` called a second time skipped the rest of the chain instead of running it again, `proceed()`
returned the constructed instance from an `@AroundConstruct` method where the specification returns nothing,
`getConstructor()` returned the constructor of the generated proxy rather than of the target class, and a binding
annotation reaching a class along two paths with different member values was silently resolved to one of them
rather than reported. The kit's own scenarios then caught the first attempt at that last fix over-reporting: a
class that states a binding itself has already answered what that binding binds by, whatever the annotations it
declares carry.

What the specification does have is an assertion catalogue: the
https://repo1.maven.org/maven2/jakarta/tck/cdi-tck-ee-impl/11.0.0.M1/cdi-tck-ee-impl-11.0.0.M1-coverage-interceptors.html[Jakarta
Interceptors Specification TCK Coverage Report] breaks it into 166 numbered assertions. This page records where this
module stands against every one of them.

=== Section 5.2 - Interceptor Ordering Rules
|===
| | Assertion | Status | Where

| a)

| Not applicable
| No default interceptors

| b)
| If a default interceptor class has superclasses, interceptor methods declared in the interceptor class’s superclasses are invoked before the interceptor method declared in the interceptor class itself, most general superclass first.
| Not applicable
| No default interceptors

| c)
| Interceptor methods declared in the interceptor classes listed in the Interceptors annotation are invoked in the same order as the specification of the interceptor classes in that annotation.
| Covered
| InterceptorsTest

| d)
| If an interceptor class declared by applying the Interceptors annotation at class-level has superclasses, interceptor methods declared in the interceptor class’s superclasses are invoked before the interceptor method declared in the interceptor class itself, most general superclass first.

| e)

| Covered

| f)

| HierarchyOrderTest

| g)
