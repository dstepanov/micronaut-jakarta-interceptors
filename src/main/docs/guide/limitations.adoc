== Not supported

Everything below belongs to a container this module is not: a Jakarta Enterprise Beans container, a deployment
descriptor, or a Contexts and Dependency Injection implementation. None of it has a counterpart here.

=== Deployment descriptors

There is no `ejb-jar.xml` and no `beans.xml`, so interceptors cannot be declared, ordered, overridden or disabled
through one. Everything is declared in annotations.

=== Default interceptors

Default interceptors apply to a whole set of target classes and are declared in a deployment descriptor, so there
are none. `jakarta.interceptor.ExcludeDefaultInterceptors` is accepted and does nothing: there is nothing for it to
exclude. It is accepted rather than rejected so that code written for a Jakarta Enterprise Beans container still
compiles.

Nor is there a way to arrive at one by the back door. An interceptor class that declares no binding annotation
intercepts nothing rather than everything, and a bean that declares no interception of its own is never
intercepted, whichever interceptors the context holds. Interception is decided where it is declared, and a bean
that declares none is not proxied at all, so there is nothing for a default interceptor to attach to. The nearest
thing is a binding annotation that is `@Inherited`, declared on a base class, which then covers everything that
extends it.

=== The enterprise naming context

An interceptor class does not share an enterprise naming context with the class it intercepts, because there is
none. Its dependencies come from the bean context, by injection.

=== Transaction and security context

The specification has an interceptor method run in the transaction and security context of what it interposes on.
Neither is part of this module: an interceptor runs in whatever context the invocation is already in, and nothing
is established or propagated on its behalf.

=== Web service endpoints

`InvocationContext.getContextData()` is always the map this module shares between the interceptors of one
invocation. It is never a `MessageContext`, since there is no web service endpoint to produce one.

=== The extension points of other specifications

An extension specification may define further sources of interceptor bindings, further ways of declaring an
interceptor, and further rules for combining bindings. Nothing here reads such an extension: no meaning is given
to `jakarta.enterprise.inject.Stereotype`, and no rule of another specification is applied.
`jakarta.enterprise.util.Nonbinding` is the exception, and is understood, because the Interceptors specification
names it itself.

A Contexts and Dependency Injection stereotype nevertheless carries its bindings across, because a binding
annotation declared on another annotation binds through it whatever that annotation is otherwise for. A class or a
method annotated with a stereotype that declares `@Monitored` declares `@Monitored`, and the interceptors bound to
it intercept the class or the method. The kit's own resolution scenarios rely on exactly that and are run here; see
<<conformance,Conformance>>, sections 3.1.2 a) and 3.3 e). What is not read is the stereotype as such - a
stereotype that names a scope, a name or an interceptor by any rule of that specification other than declaring the
binding is read as the annotation it is and no more.

=== Methods that return a future

The interception the specification describes is synchronous. A method that returns a `CompletableFuture`, or any
other value that completes later, is intercepted as it hands that value back, not as it completes: an interceptor
that measures time around `proceed()` measures the call, not the work. This is what an interceptor of an ordinary
Micronaut advice sees as well.

A Kotlin suspending function is intercepted the same way. The compiler makes it a method that returns the first time
the function suspends, returning the marker `COROUTINE_SUSPENDED` rather than a result, and completes it later by
resuming the continuation it adds after the declared arguments. `proceed()` returns that marker to the interceptor.
The code after `proceed()`, a `finally` included, therefore runs before the work that follows the suspension, and an
exception thrown once the function has resumed is thrown after the interceptor has returned, where its `catch` does
not see it. What an interceptor can rely on is everything up to the first suspension: it sees the arguments the
function declares and may replace them, the code before `proceed()` runs before the body, and the caller receives
the value the function completes with, or the exception it fails with, as long as the interceptor returns what
`proceed()` returned. Work after completion, measuring the time the function takes, and catching an exception thrown
after it resumes are out of its reach. A suspending function that completes without suspending returns its value
from the call, and is intercepted through to its completion as any other method is.

=== Interceptors registered after the first interception

The interceptor classes bound by a binding annotation are looked for among the beans once, the first time an
element bound that way is intercepted, and the chain of each element is remembered after it is resolved. An
interceptor registered with the context after that, at runtime, is therefore not picked up. Interception is
declared where it is compiled, and that is where interceptors are expected to come from.

=== A note on interceptor instances

An interceptor class becomes a bean, so an application may also produce it from a `@Factory` method to configure
the instance itself; the instance the factory produced is then the one that intercepts. The definition this module
declares for an interceptor class is a secondary one, which is what lets a factory take its place rather than the
two being ambiguous. That holds for a class declaring `@Interceptor` as much as for one only named by
`@Interceptors`.

An interceptor class that declares a scope or a bean annotation of its own, such as `@Singleton`, is a bean the
application declared rather than one this module declares, and is left as it was declared. A factory producing the
same class is then as ambiguous with it as with any other bean declared twice, unless one of the two is marked
`@Primary` or `@Secondary`.

=== What a factory method binds

A method of a `@Factory` class that declares another bean is not a business method of the factory but the
declaration of that bean, so what it binds, and the interceptor classes it names, belong to the bean it produces and
are combined with whatever the produced type declares on itself. A static factory method produces a bean the same
way and binds it the same way. The factory is a bean of its own besides, and is intercepted in its own right when it
carries a binding or declares an `@AroundInvoke` method: an interceptor method the factory declares on itself
interposes on the business methods of the factory and is never invoked on the object it produced, which is another
object of another type. A factory that is intercepted in its own right also has Micronaut intercept the producer
method, so producing the bean is intercepted once, by what the method binds, before the bean itself is.

=== Interceptor classes named on a superclass

`jakarta.interceptor.Interceptors` is not declared `@Inherited`, so a subclass does not pick up the interceptor
classes its superclass names. Declare it on the class that is the bean, or use a binding annotation that is
`@Inherited`, which is inherited as the specification describes.

=== Interceptor state on a lazy or swappable proxy target

A bean proxied with a separate target is two objects to Micronaut, and one instance of each interceptor class
serves both; see <<lifecycle,Lifecycle and Constructor Interception>>. A proxy that resolves its target only when
it is first invoked - `@Around(proxyTarget = true, lazy = true)`, and so the scoped proxies - or whose target may be
swapped - `hotswap = true` - is the exception. Its business methods are intercepted by interceptor instances of its
own, not by the ones that intercepted the construction and lifecycle of its target, so a field an interceptor sets
in a `@PostConstruct` or `@AroundConstruct` method is not seen by its `@AroundInvoke` method there. Both sets of
instances are still destroyed.

== What Micronaut requires

An element is intercepted through the proxy Micronaut generates for its bean, so the ordinary rules of Micronaut
aspect oriented programming apply:

* the intercepted class must be a bean;
* an intercepted method must not be `private`, `static` or `final`. Every other access level is intercepted, a
`protected` method included: the proxy is a subclass of the bean and overrides it as it overrides a public one;
* a call from one method of a bean to another on `this` is intercepted as long as the proxy is the bean, which it
is by default: the proxy is a subclass of the bean, so `this` is the proxy and the call goes through the method it
overrides. A bean proxied with `@Around(proxyTarget = true)` is the opposite case. Its proxy delegates to a separate
instance of the bean, `this` inside a method is that instance, and a call on it is not intercepted. A `private` or
`final` method is not intercepted in either case, since the proxy cannot override it.

Every one of these, and the whole of the specification besides, is recorded assertion by assertion under
<<conformance,Conformance>>.

== Interpreted differently

`jakarta.interceptor.AroundTimeout` interposes on the methods of a timer service that does not exist here; a
method the Micronaut scheduler invokes stands in for one. See <<timeout,Timeout Methods>>.

An object with `@AroundConstruct` interceptors is injected and initialized inside the around-construct chain
rather than after it. Micronaut constructs, injects and initializes an object in one generated method, and that
method is what the last around-construct method proceeds to; the specification completes injection only once
every around-construct method has returned. So when `proceed()` returns to an around-construct method, the fields
and methods of the object have been injected and its `@PostConstruct` callbacks - with any `@PostConstruct`
interceptor methods around them - have run. What an around-construct method does after proceeding happens after
all of that, and an exception it throws then fails an object whose post-construct callbacks have already run. The
object is still not handed to anything else until the whole chain has returned. Doing it in the order the
specification describes needs Micronaut to separate construction from injection, which this module cannot do from
outside.

A class declaring nothing but an `@AroundInvoke` method is read as an interceptor class rather than as a class
interposing on its own business methods, unless the class is a bean of its own. See
<<interceptorClasses,Interceptor Classes>>.

An array-valued member of a binding annotation is supported and compared by its contents; the specification leaves
such a member to an extension to define.

A checked exception thrown by a lifecycle callback interceptor method, which the specification does not allow it
to throw, is reported wrapped in a runtime exception: what invoked the callback is the container, and it declares
none.

The specification asks for a definition error wherever a binding reaches a `final` class or a `final` method that is
neither private nor static, since the proxy is a subclass of the bean and can override neither. A final class is
reported when a binding is declared on it or on one of its methods, as `Cannot apply AOP advice to final class`. A
class that declares or inherits a class level binding is reported for every final method it declares or inherits
that is neither private nor static, whatever its access, naming the method and the class that declared it final;
the final methods of `Object` are left out. The one case not reported is a final method that declares a binding of
its own: the binding is not applied, and the class is not proxied at all when that method is the only one bound.
See <<conformance,Conformance>>, section 3.3.

== Languages

Java, Groovy and Kotlin are supported, and each has a test suite of its own in this repository. The processor only
reads and writes annotation metadata and generates nothing, which is what lets one implementation serve the
three.

A Kotlin suspending function is intercepted up to the point it first suspends rather than until it completes, as
described under methods that return a future above, and the continuation the compiler adds after the arguments it
declares is not shown to the interceptor.

The accessors of a Kotlin property are methods of the class on the virtual machine, and are intercepted as its
functions are: a binding on the accessor - `@get:Guarded`, `@set:Guarded` - binds that accessor, and a binding on the
class binds both. A property has to be `open` to be intercepted, as a function does, because the proxy overrides its
accessors; one that is not open is left uninterceptable rather than reported, since a property the all-open compiler
plugin opens cannot be told from one that is really final.

A Groovy method whose name begins with `$` is not part of the class as far as Micronaut is concerned - the name is
reserved for what the compiler generates - so it is neither intercepted nor reported when it is final.
