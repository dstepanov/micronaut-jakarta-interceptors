The interception itself never reflects.

An interceptor method is invoked through the `io.micronaut.inject.ExecutableMethod` Micronaut generates for it at
compilation time, which dispatches through generated code. An interceptor method that has no executable method is
an error at resolution rather than a fall back to reflection, so there is no path through
`java.lang.reflect.Method` for an invocation to take. The interceptor chain of an element is read from the
annotations the processor left on it, the interceptor instances come from the bean context, and the proxy of an
intercepted bean is a generated subclass.

Three accessors of `InvocationContext` do reach for the reflection of the platform, because the types the
specification has them return leave no choice:

* `getMethod()` returns a `java.lang.reflect.Method`;
* `getConstructor()` returns a `java.lang.reflect.Constructor`;
* `getInterceptorBindings()` returns instances of the binding annotations.

All three are resolved only when an interceptor asks for them, and remembered afterwards. An application whose
interceptors do not call them never reflects at all; the binding comparison the interception does is made against
the annotation metadata Micronaut recorded at compilation time, and builds no annotation.

In a GraalVM native image such a lookup answers only for a member the image was told to keep. The processor
declares `@ReflectiveAccess` on the members the specification has these accessors return - the constructor of a
bean whose construction is intercepted, its lifecycle callbacks and the business methods that are intercepted -
which `micronaut-graal` turns into the reachability metadata of the image while it compiles the application.
`getMethod()` and `getConstructor()` therefore answer inside an image as they do on a virtual machine, and an
application declares nothing for them. Only the members that are actually intercepted are kept.

`getInterceptorBindings()` is the one that is not covered. Micronaut builds an annotation instance as a dynamic
proxy of the annotation type together with api:core.annotation.AnnotationValueProvider[], and neither
`@ReflectiveAccess` nor `@ReflectionConfig(accessType = DYNAMIC_PROXY)` can declare a proxy of two interfaces. An
interceptor that asks for the bindings inside a native image needs the pair declared by hand:

[source,json]
----
{
  "reflection": [
    {
      "type": {
        "proxy": [
          "com.acme.Logged",
          "io.micronaut.core.annotation.AnnotationValueProvider"
        ]
      }
    }
  ]
}
----

That is verified rather than asserted. The `test-suite-graalvm` module runs inside a native image through the
`nativeTest` task, and its interceptors call all three accessors: an interception that reached for reflection the
image was not told about would fail there rather than pass unnoticed on the JVM. The one entry that module
declares is the proxy above, which is exactly the gap.

An application whose interceptors call none of the three needs nothing at all. Nothing else of the interception -
the chains, the bindings, the ordering, the invocation of the interceptor methods, the parameters, the lifecycle
and the construction - asks for any metadata.
